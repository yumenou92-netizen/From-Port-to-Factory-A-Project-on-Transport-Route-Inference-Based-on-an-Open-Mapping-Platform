# 数据使用和流向说明

## 1. 文件目的

本文用于说明“北港至客户工厂全链路运输路径推断原型”当前如何使用数据、数据在系统中的流向、费用和时间单位如何处理，以及哪些数据在进入路径搜索前必须先做标准化。

当前系统仍处于原型阶段。本文不是生产系统的数据治理规范，而是后续继续开发、向领导解释、和业务人员确认口径时使用的说明文件。

## 2. 当前数据来源

当前本地 JSON 数据通过环境变量 `DATA_DIR` 指定目录，不允许在业务代码中硬编码 D 盘绝对路径。

本次审计的数据目录包含 3 类 JSON Lines 文件：

| 文件 | 当前记录数 | 主要用途 | 是否可直接形成运输边 |
|---|---:|---|---|
| `运价表.json` | 492 | 维护始发、到达、运输方式、包装方式、适用品种、费用、费用单位、价格来源、维护日期 | 可以形成候选运输边，但费用必须先换算 |
| `地点经纬度.json` | 263 | 维护港口、码头、铁路站、客户工厂等地点名称和经纬度 | 不可以单独形成运输边 |
| `其他费用表.json` | 18 | 维护节点作业费、提柜费、装卸费、过闸费等附加费用 | 不可以单独形成运输边 |

## 3. 数据总体流向

当前推荐的数据流向如下：

```text
本地 JSON 数据目录 DATA_DIR
        ↓
数据读取与审计
        ↓
地点名称标准化
        ↓
生成或匹配 Node
        ↓
从运价表生成候选 FreightRate / TransportEdge
        ↓
按订单数量、包装方式、费用单位换算为运输段总费用
        ↓
最后一公里先识别既定路线；无既定运价再按规则和地图距离估算
        ↓
补充运输时间
        ↓
按业务规则过滤不可行边
        ↓
构建图结构
        ↓
分别按 cost 和 time 搜索路径
        ↓
输出成本最低路径和时效最优路径
```

当前阶段已经完成的是“数据读取与审计”。后续进入路径搜索前，必须先完成地点标准化、费用单位换算、时间补充和业务规则过滤。

## 4. 三类数据的使用方式

### 4.1 `运价表.json`

`运价表.json` 是当前最接近运输边的数据来源。

核心字段：

| 字段 | 用途 |
|---|---|
| `始发` | 候选运输边起点名称 |
| `到达` | 候选运输边终点名称 |
| `运输方式` | 运输方式，目前包括汽运、驳船 |
| `包装方式` | 区分散粮、集装箱 |
| `适用品种` | 判断订单货物是否适用 |
| `费用` | 原始报价数值 |
| `费用单位` | 解释费用数值的单位，目前包括元/吨、元/箱 |
| `价格来源` | 记录费用来源，例如集采、询价、临采成交 |
| `维护日期` | 记录价格维护日期 |

使用限制：

- `费用` 不能直接作为路径搜索的 `cost` 使用。
- `费用单位` 不同的数据不能直接相加。
- `元/吨` 必须结合订单吨数换算为该运输段总费用。
- `元/箱` 必须结合订单箱量换算为该运输段总费用。
- 如果同一始发、到达、运输方式下存在不同包装方式、适用品种、价格来源，应保留为不同候选边或不同费率记录。
- 如果同一路线存在多次维护记录，应按时间标签选择最新记录作为当前既定运价。

### 4.2 `地点经纬度.json`

`地点经纬度.json` 用于生成或补充 `Node`。

核心字段：

| 字段 | 用途 |
|---|---|
| `名称` | 地点名称，用于和运价表中的始发、到达匹配 |
| `经度` | 地点经度 |
| `纬度` | 地点纬度 |

使用限制：

- 该文件没有运输方式、费用、时效，不能单独生成运输边。
- 经纬度可用于候选中转港初筛，但不能只按直线距离决定最终路径。
- 发现明显别名时，必须先维护名称映射，例如 `郴州南` 和 `郴州南站`、`怀化西` 和 `怀化西站`。
- 同一个物理节点只能对应一个 `node_id`。尤其是“第一阶段终点南方港口”和“第二阶段起点南方港口”必须是同一个节点。

### 4.3 `其他费用表.json`

`其他费用表.json` 用于补充节点附加费用。

核心字段：

| 字段 | 用途 |
|---|---|
| `节点简称` | 费用发生的港口、码头、铁路站或其他节点 |
| `包装类型` | 区分散粮、集装箱 |
| `费用类型` | 作业费、提柜费、装卸费、过闸费等 |
| `单价` | 原始附加费用数值 |
| `费用单位` | 单价单位，例如元/吨、元/箱 |

使用限制：

- 该文件不能单独形成运输边。
- 附加费用只能在匹配到具体运输段、节点、包装方式和订单数量后，计入该段总费用。
- 同一节点可能存在多类费用，不能默认全部叠加，必须由业务规则说明哪些费用适用于当前路线。

## 5. 单位使用声明

### 5.1 费用单位声明

路径搜索内部使用的 `cost` 必须统一为：

```text
当前订单在该运输段上的总费用，单位：元
```

原始台账中的费用单位包括：

| 原始单位 | 含义 | 进入路径搜索前的换算方式 |
|---|---|---|
| `元/吨` | 每吨费用 | `运输段总费用 = 单价 × 订单吨数` |
| `元/箱` | 每箱费用 | `运输段总费用 = 单价 × 订单箱数` |

业务声明 1：运价表中运费单位可以不完全统一，但用户输入的订单数量单位必须和该条运价的费用单位匹配。只要二者匹配，系统最终能换算出金额，单位为元，就可以接受计算。

示例：

| 用户输入 | 运价单位 | 判断结果 | 原因 |
|---|---|---|---|
| `500 箱/柜` | `250 元/箱` 或 `250 元/柜` | 接受 | 数量单位和运价单位匹配，可计算总费用 |
| `500 吨` | `250 元/吨` | 接受 | 数量单位和运价单位匹配，可计算总费用 |
| `500 吨` | `250 元/箱` 或 `250 元/柜` | 拒绝 | 数量单位和运价单位不匹配，不能直接相乘 |
| `500 箱/柜` | `250 元/吨` | 拒绝 | 数量单位和运价单位不匹配，不能直接相乘 |

因此，系统在费用换算前必须先做单位匹配校验。校验不通过时，应输出清晰错误提示，不接受该次输入，也不将该条费用写入路径搜索权重。

禁止行为：

- 禁止把 `元/吨` 和 `元/箱` 的原始数值直接相加。
- 禁止把原始 `费用` 字段直接写入图的 `cost`。
- 禁止在没有订单数量的情况下声称已经得到真实总费用。
- 禁止把费用异常值直接删除；应先结合费用单位、包装方式和运输距离判断。

允许行为：

- 可以在数据审计阶段统计原始费用。
- 可以在路径搜索前保存原始费用和原始单位，作为解释字段。
- 可以在换算后生成 `normalized_total_cost`，再作为图边的 `cost`。

### 5.2 时间单位声明

路径搜索内部使用的 `time` 必须统一为一种固定单位。建议第一阶段统一为：

```text
小时
```

当前 JSON 数据没有运输时效字段，因此：

- 散船运时当前只能由用户人工输入。
- 汽运、驳船、铁路等运输时效需要后续补充数据源或人工维护。
- 在缺少时间数据时，不能输出可靠的“时效最优路径”。
- 允许在原型阶段使用人工维护的时间，但必须标记时间来源。

后续建议统一设计 `ShippingTimeProvider`：

| Provider | 当前状态 | 用途 |
|---|---|---|
| `ManualShippingTimeProvider` | 当前启用 | 人工输入运输时间 |
| `JsonShippingTimeProvider` | 预留 | 从 JSON 文件读取运输时间 |
| `DatabaseShippingTimeProvider` | 预留 | 从数据库读取运输时间 |
| `ApiShippingTimeProvider` | 预留 | 从外部 API 获取运输时间 |

## 6. 节点和边的形成规则

### 6.1 Node

`Node` 表示物流网络中的地点。

来源包括：

- `地点经纬度.json` 中的 `名称`、`经度`、`纬度`。
- `运价表.json` 中出现但坐标表缺失的 `始发`、`到达`。
- 后续客户信息表中的客户工厂、自有码头。

建议字段：

| 字段 | 说明 |
|---|---|
| `node_id` | 标准节点编号，系统内部唯一 |
| `node_name` | 标准节点名称 |
| `node_type` | 港口、码头、铁路站、客户工厂、仓库等 |
| `longitude` | 经度 |
| `latitude` | 纬度 |
| `aliases` | 别名列表 |
| `is_active` | 是否启用 |

声明：

- `node_id` 不能由临时显示名称随意生成后长期使用，必须可维护。
- 同一物理地点只能有一个标准 `node_id`。
- 别名只能映射到标准节点，不能作为独立节点直接参与路径搜索。

### 6.2 TransportEdge

`TransportEdge` 表示两个节点之间可以走的一段运输关系。

可从 `运价表.json` 初步生成：

| 字段 | 来源 |
|---|---|
| `from_node_id` | `始发` 映射到标准 Node |
| `to_node_id` | `到达` 映射到标准 Node |
| `transport_mode` | `运输方式` |
| `package_type` | `包装方式` |
| `commodity_scope` | `适用品种` |
| `price_source` | `价格来源` |
| `raw_price` | `费用` |
| `raw_price_unit` | `费用单位` |
| `normalized_total_cost` | 按订单换算后的运输段总费用 |
| `time_hours` | 统一后的运输时长，单位小时 |

声明：

- 同一始发和到达之间可能存在多条边，例如不同运输方式、包装方式、价格来源或费用单位。
- 后续图结构应优先评估 `nx.MultiDiGraph`，避免同一对节点之间的多条候选边被覆盖。
- 路径结果不能只返回节点列表，还必须返回具体采用的边、运输方式、费用、时间和价格来源。

## 7. 成本和时效的使用声明

系统必须分别维护两套权重：

```text
cost = 当前订单该运输段总费用
time = 当前订单该运输段总耗时
```

声明：

- 成本最低路径按 `cost` 单独搜索。
- 时效最优路径按 `time` 单独搜索。
- 在没有业务确认权重系数前，禁止将 `cost` 和 `time` 合并成单一综合权重。
- 如果某条边缺少费用或时间，应标记缺失，不应默认写成 0。

## 7.1 最后一公里汽运数据使用声明（2026-07-10 16:26）

最后一公里汽运阶段分为“熟悉线路”和“陌生路线”两种处理方式。

### 熟悉线路

如果南港到客户工厂的路线已经存在于既定路线库，则直接使用维护好的确切运费。

要求：

- 路线识别至少需要起点、终点、运输方式、包装方式。
- 如果同一路线有多条维护记录，必须按时间标签取最新记录。
- 结果输出中必须保留价格来源和维护时间。

### 陌生路线

如果既定路线库中没有对应运价，则需要：

1. 调用地图距离 Provider 获取公路距离。业务口径指定为腾讯地图 API。
2. 根据包装方式选择散粮或集装箱汽运规则。
3. 得到单位运价后，再按订单数量换算为该运输段总费用。

当前阶段仅声明该数据流向，不直接实现腾讯地图 API。

散粮规则：

| 距离范围 | 单吨计费规则 |
|---|---|
| `X <= 20 公里` | `15 元/吨` 一口价 |
| `20 < X <= 30 公里` | `20 元/吨` 一口价 |
| `30 < X <= 100 公里` | `0.5 元/吨/公里 × X` |
| `100 < X <= 150 公里` | `0.4 元/吨/公里 × X` |
| `X > 150 公里` | `0.3 元/吨/公里 × X` |

集装箱规则：

| 距离范围 | 单箱计费规则 | 折合单吨 |
|---|---|---|
| `X <= 20 公里` | `Y = 500 元/箱` | `Y / 30 元/吨` |
| `X > 20 公里` | `Y = 500 - (X - 20) × 30 × 0.55 元/箱` | `Y / 30 元/吨` |

待确认：

- `X > 20` 的集装箱公式随距离增加而降低费用，实现前需要再次确认公式方向。
- `元/箱` 到 `元/吨` 暂按 `30 吨/箱` 折算，该箱重是否固定适用于所有订单需要业务确认。

## 8. 当前数据能支持什么

当前数据可以支持：

- 初步生成汽运和驳船候选运输关系。
- 建立地点名称和经纬度基础表。
- 识别部分港口、码头、铁路站和客户工厂名称。
- 统计费用单位、包装方式、适用品种和价格来源。
- 为后续候选中转港筛选提供坐标基础。
- 为熟悉线路直接取既定运费提供路线库基础。

当前数据不能单独支持：

- 完整的北港到南港散船干线报价。
- 完整的运输时间计算。
- 自动获取腾讯地图公路距离。
- 客户是否有自有码头判断。
- 第一阶段和第二阶段南方港口节点统一。
- 直接输出生产级成本最低和时效最优路线。
- 在不提供订单吨数或箱数的情况下计算真实总费用。

## 9. 需要业务确认的声明项

以下内容需要业务侧确认后，才能进入正式路径计算：

1. 订单数量字段：按吨计费时使用哪个订单字段，按箱计费时使用哪个订单字段。
2. 箱量和吨数换算关系：是否存在固定箱重，还是必须由订单录入。
3. `元/箱` 是否按自然箱、集装箱规格、或业务结算箱定义。
4. 驳船费用是否只适用于散粮，还是也适用于集装箱。
5. `其他费用表.json` 中哪些费用类型应叠加到哪一段运输。
6. `维护日期` 缺失时，该报价是否仍可使用。
7. 同一线路多条报价并存时，优先使用最新日期、指定价格来源，还是全部作为候选。
8. 客户自有码头数据由哪个表维护。
9. 运输时间由人工输入、台账维护，还是后续接入外部接口。
10. 南方港口标准节点清单和别名映射由谁维护。
11. 腾讯地图 API 的密钥、调用额度、距离口径和失败时的降级方式。
12. 集装箱汽运 `20 公里以上` 公式是否确认为 `500 - (X - 20) × 30 × 0.55`。

## 10. 建议后续落地顺序

建议按以下顺序推进，避免把未标准化的数据直接写入图：

1. 建立地点标准化表：标准 `node_id`、标准名称、别名、经纬度。
2. 明确订单输入结构：吨数、箱数、包装方式、品种、目标客户。
3. 建立费用换算函数：将 `元/吨`、`元/箱` 换算为运输段总费用。
4. 建立时间输入接口：先启用人工时间输入。
5. 将 `运价表.json` 转为候选 `FreightRate`。
6. 根据客户、自有码头、包装方式、品种过滤候选边。
7. 构建 `MultiDiGraph`，分别以 `cost` 和 `time` 搜索。
8. 输出路径时保留每段边的来源、原始单位、换算后费用和时间来源。

## 11. 当前阶段结论

当前 JSON 数据已经具备“生成候选运输边和节点基础表”的条件，但还不能直接进入路径搜索。关键原因是：

- 费用单位尚未统一到订单段总费用。
- 时间数据缺失。
- 地点名称尚未标准化为 `node_id`。
- 客户自有码头和业务过滤规则尚未接入。

因此，当前正确做法是先完成数据标准化和单位声明，再进入图构建和路径搜索。
