# 阶段展示前双轨开发计划与 SOP

日期：2026-07-29
适用阶段：阶段 18 数据夯实、真实驳船构边与阶段性领导展示准备

## 一、目标与边界

阶段展示前采用两条并行主线：

1. 数据确认线：持续确认港口水域角色、别名、包装能力和散粮准入；
2. 工程开发线：继续推进不依赖未确认业务数据的接口、构图、审计和 Demo 稳定性工作。

两条线互不等待，但任何未确认的费用、时效、包装换算、港口能力或物理连通性都不得由代码猜测。缺失值不得补 0；占位只能使用明确的 `demo_placeholder`。

## 二、当前可复现基线

- 真实运价：492 条；
- 标准节点：367 个；
- 已计费且两端节点完整的基础候选：312 条；
- 北港散船自动南港候选：9 个，均具有明确海港或海河双用标识；
- 闽江当前仅维护 `南平港 ↔ 军航码头`；
- 该驳船段适用于散粮玉米、小麦，双向均为 50 元/吨、完整运输时间 15 小时；
- 南平港支持散粮、集装箱、驳船和铁路，但作为纯内河港不得成为北港散船南港终点；
- 当前客户工厂均按无自有码头处理；
- 最近全量测试：`413 passed`；real-data smoke 通过。

## 三、数据确认线

### D1. 港口水域角色一次性确认

输入：

- `output/south_port_waterway_role_confirmation_2026-07-29.csv`

每个节点至少确认：

1. 水域角色：`sea_port`、`sea_inland_dual_use`、`inland_port` 或 `ignore`；
2. 是否可承接北港散粮散船；
3. 对散粮是否支持玉米、小麦；
4. 是否与清单中的其他名称属于别名、港区关系或独立物理节点。

### D2. 确认结果处理

1. 先核对名称字典和 0729 码头工作簿；
2. 同一物理节点只保留一个稳定 node ID；
3. 别名冲突、坐标冲突或多个节点同时命中时停止自动处理；
4. 用户确认后，先生成变更预览和受影响候选数量；
5. 用户审核预览后才写入正式能力/角色数据；
6. 写入后重跑订单—港口准入审计；
7. 对新增海港候选检查散船费率、航时和作业费，三项不完整时仍不得入图。

### D3. 数据确认交付物

- 完整确认清单；
- 别名合并建议；
- 标准节点 ID 变更预览；
- 海港/内河港/忽略节点统计；
- 新增可入图候选及阻塞原因清单。

## 四、工程开发线

### E1. 闽江三段式路径接入

状态：第一版已完成并通过专项测试；等待用户 PyCharm 真实 Tencent 道路预演。

目标路径：

```text
北港
-> 军航码头（北港散船）
-> 南平港（闽江驳船）
-> 客户工厂（汽运）
```

开发事项：

1. 在现有 `MultiDiGraph` 中加入海港—内河港驳船中转边；
2. 复用正式驳船 Provider，生成军航码头—南平港双向边；
3. 从南平港到客户工厂继续使用已维护汽运价或腾讯道路距离规则；
4. 保留北港散船、码头作业费、驳船费和汽运费四类费用组成；
5. cost/time 继续独立 Dijkstra，不新增综合权重；
6. 与“南港直接汽运到客户”的路线作为平行方案比较；
7. 马尾港和其他未维护闽江端点不得生成驳船边。

### E2. 领导 Demo 展示收束

1. 输出每个候选被纳入或排除的原因；
2. 显示海港标识来源、别名来源和能力来源；
3. 显示完整费用组成和完整运输时间；
4. 驳船线仍明确标记为示意几何，不能宣称真实航道；
5. 若确认海港不足导致无路线，返回可读的数据缺口，不回退未知港口；
6. 保留 AdditionalFee 未确认归属的警告。

### E3. Web 展示页同步

1. 支持展示三段或四段路线；
2. 北港散船继续使用近海虚线；
3. 汽运继续使用腾讯真实道路折线；
4. 闽江驳船使用单独颜色和明确“示意航道”标签；
5. 页面显示节点角色、运输阶段、费用组成、来源和警告；
6. 用户指定南港时仍必须经过海港标识与散粮能力校验。

### E4. 审计与测试

1. 玉米、小麦分别覆盖代表重量和船型边界；
2. 覆盖自动南港和人工指定南港；
3. 覆盖未知港、纯内河港、仅集装箱港和忽略节点；
4. 覆盖军航—南平正向、反向以及非法闽江端点组合；
5. 先运行专项测试；
6. 只有核心数据 Loader、候选准入或构图主链变化时运行全量 smoke；
7. Tencent 实时调用由用户在 PyCharm 执行，Codex 环境失败只能记为 `manual_review`。

## 五、双轨 SOP

### 每轮开始

1. 检查 Git 状态、暂存区和任务外材料；
2. 读取最新确认清单和上一轮审计；
3. 判断本轮工作属于“可独立开发”还是“必须业务确认”；
4. 对可独立开发事项直接推进，对业务歧义停止并提交用户审核。

### 数据确认回填

1. 接收用户确认；
2. 检查是否与既有决策冲突；
3. 生成别名、节点角色、能力和候选影响预览；
4. 不自动覆盖正式数据；
5. 用户确认预览后再应用；
6. 重跑只读审计并输出差异。

### 代码实现

1. 优先修改 Provider、类型化记录和审计层；
2. 不让路由算法直接读取 Excel、JSON 或未来数据库；
3. 所有数据源通过相同领域对象进入构图层；
4. 缺费用、距离或时间时不创建可搜索边；
5. 保持 `MultiDiGraph` 平行边和 cost/time 独立搜索；
6. 只修复当前展示与阶段 18 主线有关的问题。

### 验证与交付

1. 运行最小相关专项测试；
2. 核心主链变化时运行 `python -B -m src.dev.smoke_test`；
3. 生成可复现审计文件；
4. 更新 `PLAN.md`、`PROJECT_STATE.md`、`DECISIONS.md` 和 `CHANGELOG.md`；
5. 明确区分真实数据、确认规则、地域代理和 `demo_placeholder`；
6. 未经明确要求不提交或推送 Git；
7. GitHub 提交使用文件白名单，禁止 `git add .`。

## 六、立即执行顺序

1. 用户开始分批回复港口确认清单；
2. 用户在 PyCharm 预演已接入的 E1“军航码头—南平港—客户工厂”三段式路径；
3. 工程侧继续 E2，收束 leader full-flow 的候选排除原因和中转费用展示；
4. 再完成 E3 Web 页面中转节点样式和交互检查；
5. 每批港口确认完成后刷新候选准入审计，不阻塞 E2/E3 开发；
6. 出现新费用、时效、单位换算或能力歧义时停止并提交用户确认。
