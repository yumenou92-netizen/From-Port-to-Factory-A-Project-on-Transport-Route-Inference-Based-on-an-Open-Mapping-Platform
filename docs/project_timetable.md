## 2. 各阶段工作与验收

### 阶段 1：数据审计修正（当前最小收尾）

**应该做什么**

- 将费用异常检测按 `费用单位` 分组，避免混合比较 `元/吨` 和 `元/箱`。
- Git 可跟踪报告只保留脱敏汇总；真实名称、路径和费用示例只写入本地 `output/`。

**验收标准**

- `docs/` 报告不包含绝对路径、真实客户/地点名称和费用明细。
- 本地详细报告仍可支持人工排查。

### 阶段 4：FreightRate 与费用换算（下一主开发阶段）

**应该做什么**

- 定义正式 `FreightRate`，保留原始价格、单位、价格类型、来源和维护日期。
- 接入散船指数测算和人工报价，人工报价显式区分 `unit_price` / `total_price`。
- 台账运价换算为当前订单运输段总费用。
- 其他费用按订单单位换算后追加，禁止直接相加不同原始单位。
- 熟悉线路按路线和时间标签选择最新有效运价。
- 为陌生路线预留 `DistanceProvider`，暂不连接腾讯地图 API。

**验收标准**

- 所有可用费用输出为 `total_cost_yuan`。
- 原始价格、原始单位和价格来源仍可追溯。
- 缺少数量、单位不支持或价格异常时进入人工确认。
- 同一路线多条维护记录能够选择最新有效价格。
- 外部地图接口没有被硬编码进计费模块。

### 阶段 6：CustomerProfile 与业务规则过滤

**应该做什么**

- 定义客户工厂、自有码头、允许包装和品种等字段。
- 有自有码头：南港 -> 客户自有码头 -> 完成交付。
- 无自有码头：南港 -> 候选中转港 -> 短途汽运 -> 客户工厂。
- 候选中转港先按距离筛前 K，再比较总费用和总时间。

**验收标准**

- 两类客户不会生成相互矛盾的路线。
- 候选港筛选原因、K 值和后续比较过程可解释。
- 缺少客户画像时停止推荐并提示补充数据。

### 阶段 7：TransportEdge

**应该做什么**

- 将标准节点、标准费率、订单、客户规则和运输时间组合成候选边。
- 保留 `cost` 与 `time_hours` 两套独立权重。
- 节点不完整、费用或时间缺失的记录明确进入不可用或人工确认状态。
- 同一节点对的不同运输方式、包装或来源均保留。

**验收标准**

- 每条边能追溯费用、时间、距离和数据来源。
- 只有节点、费用和必要业务条件完整的边进入正式图结构。
- 不会因为节点对相同而覆盖另一条业务边。

### 阶段 8：MultiDiGraph

**应该做什么**

- 使用 `nx.MultiDiGraph` 存储标准节点和多条平行运输边。
- 将 `cost`、`time_hours`、运输方式和来源写入边属性。
- 建立稳定 edge key，确保路径结果能定位具体边。

**验收标准**

- 同一节点对的多条边全部存在。
- 图中节点不存在重复物理地点。
- cost 和 time 没有合并成综合权重。

### 阶段 9：RouteSearchStrategy

**应该做什么**

- 定义统一搜索策略接口。
- 使用 NetworkX Dijkstra 作为基线。
- 分别运行成本最低和时间最短搜索。
- 路径结果必须返回 node_id、edge key 和每段属性。

**验收标准**

- 同一订单分别得到成本最低和时间最短结果。
- 两类结果可能不同，且原因可以逐段解释。
- 没有业务权重系数时绝不输出综合最优路径。
