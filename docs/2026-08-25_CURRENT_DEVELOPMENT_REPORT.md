## 2. 原始设想与当前架构的连续性

0710 V2 已确立的主线是：**规则驱动的候选路径生成 + 有向加权图检索 + 分段费用/时效计算**。其目标是从北方起点到客户工厂生成多套方案，并分别输出费用最低和时效最优结果，而不是为某一条散船路线编写专用脚本。

当前工程延续了该目标，但将早期概念模型收束为更严格的正式契约：

```text
本地业务数据 / 地图结果 / 维护规则
        ↓
数据标准化、节点解析、订单与单位校验
        ↓
各运输方式 Provider 生成可审计的 TransportEdge
        ↓
nx.MultiDiGraph 保留同 OD 的平行运输方案
        ↓
费用最低 Dijkstra        时间最短 Dijkstra
        ↓                         ↓
RouteResult：分段费用、时效、规则、来源、缺口提示
        ↓
RoutePlanningService → CLI Demo / Web 适配器
```

早期 `DiGraph` 已升级为 `nx.MultiDiGraph`，因为同一对节点之间可能同时存在不同运输方式、不同箱型、不同报价条件或不同中转组合。费用与时间保持两套独立搜索，不构造未经确认的综合权重。

## 3. 已确认的业务分类与节点语义

### 3.1 包装方式与北—南干线运输方式

| 业务维度 | 当前确认值 | 说明 |
|---|---|---|
| 包装方式 | 散粮、集装箱 | 用于订单准入和计费单位校验，不自动推导运输方式。 |
| 北—南干线运输方式 | 散船（散粮船运） | 仅适用于散粮。 |
| 北—南干线运输方式 | 集装箱铁路运输 | 仅适用于集装箱。 |
| 北—南干线运输方式 | 集装箱船运 | 仅适用于集装箱。 |
| 北—南干线运输方式 | 船铁联合运输 | 仅适用于集装箱；由船运与铁路边组合，但整体仍属于北港至南港业务段。 |

### 3.2 北港、南港与北站、南站不是同一类节点

- 北港、南港表示航运码头或港口节点；北站、南站表示铁路站点。
- 港口不能仅因名称、地理相近或存在客户运价而被当作铁路站；铁路站也不能被当作可接收海运货物的南港。
- 某些节点可同时具有港口和铁路能力，可分别作为航运 OD 与铁路 OD；这是节点标签和能力数据确认后的结果，不是默认推断。
- 一般节点只具备其中部分能力。是否可生成边，应由标准 `node_id` 对应的节点基础设施类型、业务角色、可处理包装、粮食品种、可用运输方式、连通性与确认状态共同决定。

### 3.3 两个业务运输段不变

长期模型仅有：

1. `north_to_south`：北港至南港；
2. `south_to_customer`：南港至客户工厂。

业务运输段不等于图边数量。一个阶段可由一条或多条边组成，也可由同种或不同运输方式组成。`transport_stage`、`transport_mode`、`edge_role`（`trunk` / `transfer` / `delivery`）必须分别记录。

## 5. 当前可复用的正式工程能力

### 5.1 数据、领域与地理层

- 本地真实数据读取、数据质量审计、最新有效维护运价选择和节点别名/坐标解析；
- `NodeRegistry` 以标准 `node_id` 管理名称、别名和坐标，冲突或不唯一保持人工复核；
- `RouteRequest` 对包装、计费单位、订单数量和品种进行校验，`吨`、`箱`、`柜`不自动换算；
- Tencent 地点检索、道路距离和道路时效通过独立 geo Provider 提供；网络、权限或候选歧义均应保留为结构化问题；
- 费用规则、原始单位、来源、规则编号/版本、维护日期和计算过程可追溯。

### 5.2 图、搜索与结果层

- `TransportEdge` 只有在端点、费用、时效、单位、来源和必要业务条件完整时才可进入正式图；缺失不默认补零；
- `nx.MultiDiGraph` 用稳定 edge ID 保存平行边；
- 费用最低和时间最短独立执行 Dijkstra；
- `RouteResult` 输出每条实际边的业务段、运输方式、边角色、费用组成、时效、数据来源、规则和警告；
- `RoutePlanningService` 是界面无关入口，现有 CLI 和本地 Web 不应再维护独立计费或搜索逻辑。

### 5.3 散粮散船已形成的能力边界

- 北港至具备确认准入条件的南港，可使用真实散船报价、订单吨数和确认的完整航运段时效生成散船干线边；
- 南港作业费通过独立 Provider 计入可解释费用组成；未确认费用不得默认为零；
- 第二阶段可比较已维护汽运、已确认陌生汽运规则，以及当前已有完整能力/费率/时效数据支持的驳船中转接续；
- 节点能力、包装、品种、运输方式、港口海河属性和连通性是构边条件，不能由地名关键词、坐标接近或单条报价记录替代；
- 当前地图中的散船/驳船线是控制点示意，汽运线才使用同次腾讯道路折线；地图几何不参与费用、时效或最短路计算。

## 7. 当前铁路集装箱开发状态

铁路集装箱不是散粮散船规则的变形，而是集装箱订单下独立的北—南干线 Provider。当前已完成：

- 北站—南站铁路干线的费用组成原型：铁路执行运价、上站费、下站费，以及敞顶箱篷布费；
- 东北至福建、广东、广西的完整铁路时效口径已作为待数据化的确认规则；
- `柜` 不换算为 `箱`；测试/演示占位来源必须明确标注 `demo_placeholder`；
- 铁路末端汽运规则与通用集装箱汽运规则保持隔离的设计方向；
- 已形成双轨 SOP：数据确认线和工程开发线可以并行，但真实构边必须等待完整准入。

铁路正式入图前的硬门禁为：

1. 北站、南站均已解析为唯一且确认的标准 `node_id`；
2. 订单包装、计费单位、品种、贸易类型和箱型满足记录要求；
3. 铁路运价、上/下站费、折扣仅接受精确站点或精确 OD 匹配，**不得使用地域代理或最近站代理**；
4. 时效仅在两端铁路站均有唯一、已确认的区域归属后匹配；没有区域映射或区域不唯一即人工复核；
5. 铁路站能力与港口能力分开管理；不得借用驳船/海港能力构边；
6. 南站至客户的接续方案须有独立、可追溯的数据或已确认规则；客户专用线、第三方专用线和船铁联合运输继续冻结。

对应实施计划见 `docs/plans/2026-08-25-001-feat-rail-container-sop-plan.md`。

## 9. 建议的下一步开发顺序

1. 先确认铁路数据表的精确业务键、价格类型、站点费适用范围、折扣条件，以及北站/南站到确认区域的维护方式；
2. 实现铁路数据模板、保守 Loader 和只读准入审计；
3. 用标准 node ID、精确 OD 运价、精确两端站费和确认时效生成正式铁路干线边；
4. 再实现铁路南站至客户的独立末端接续 Provider；
5. 只有至少一条真实铁路方案通过审计和专项集成测试后，才把铁路方案接入 `RoutePlanningService`、CLI 与 Web；
6. 船铁联合运输另行收集换装、班列/船期、费用、时效、能力和连接关系数据后再单独规划。

## 10. 当前结论

项目已经从早期“CSV/JSON + 单层有向图原型”发展为可复用的、面向多运输方式的路径推断核心：公共层负责节点、订单、费用追溯、地理信息、正式图与双目标搜索；各运输方式 Provider 负责自身的能力准入、费率、时效和费用组成。

散粮散船及其当前数据支持的第二阶段接续已形成可运行闭环；集装箱船运、集装箱铁路运输和船铁联合运输仍应按各自数据完整度逐项准入。节点标签是连接“港口/铁路站等物理设施”与“可参与何种运输方案”的关键数据基础，不能用名称、经验或展示需求替代。
